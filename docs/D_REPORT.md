# ICU-SEWS D 담당 개발 진행 보고서

- 담당자: 임경수
- 담당 범위: Streamlit 대시보드 및 FastAPI 연동

## 1. 진행 현황 요약

D 담당의 목표는 Streamlit 기반 대시보드 UI를 구성하고, FastAPI의 상태 확인 및 예측 API를 연동하여 사용자가 환자 관찰값과 예측 결과를 확인할 수 있도록 하는 것이다.

주요 작업은 다음 두 파일을 중심으로 진행했다.

- `src/icu_sews/dashboard/app.py`
- `src/icu_sews/dashboard/api_client.py`

주요 개발 및 검증 결과는 다음과 같다.

1. **대시보드 기본 UI 구현:** 환자 선택, 생체징후 입력 슬라이더, 차트·표, 위험도 요청 결과 표시
2. **FastAPI 연동:** `/health` 상태 확인 및 `/predict` 예측 요청 흐름 구현
3. **API 호출 안정성 개선:** 요청 타임아웃, 제한된 재시도, JSON 응답 형식 검증, 오류 안내
4. **자동 품질 검사 통과:** GitHub Actions에서 Ruff 검사, 포맷 검사 및 pytest 통과
5. **로컬 실행 확인:** Docker로 서비스를 실행하고 대시보드와 API 문서 접속 및 위험도 요청 결과 표시 확인

기본적인 대시보드와 API의 데모 통합은 확인했다. 다만 현재 화면에는 Mock 예측 결과가 표시되므로, 실제 모델 기반 예측과 임상 지표의 유효성 검증은 별도 작업으로 남아 있다.

## 2. 상세 구현 내용

### 2.1 대시보드 UI (`app.py`)

- 합성 데모 환자 `DEMO-001`, `DEMO-002`, `DEMO-003`을 선택할 수 있는 메뉴를 구성했다.
- 호흡수(Resp), 심박수(HR), 수축기혈압(SBP), 평균동맥압(MAP), 젖산(Lactate)을 조절할 수 있는 슬라이더를 추가했다.
- 데모 관찰값을 24시간 형태의 데이터프레임으로 구성하고, 시계열 차트와 표 탭에서 확인할 수 있도록 했다.
- 선택한 환자의 관찰값을 `/predict` 요청 데이터(payload)로 전달하고, 응답에 포함된 위험 점수, 위험 수준, 환자 ID, 모델 버전 및 시각을 화면에 표시하도록 했다.
- API 응답에 `top_features`가 포함된 경우 특징값을 표로 표시하도록 했다.
- 응답에 `feature`와 `shap_value` 필드가 제공되는 경우 관련 정보를 차트로 표시하도록 구성했다. 단, 화면에 특징값이 표시된다는 사실만으로 실제 SHAP 분석이 수행되었다고 볼 수는 없다.
- SOFA 구성요소, qSOFA 및 Calibration 지표는 API 응답에 해당 정보가 포함된 경우에만 표시하도록 했다. 정보가 없으면 값을 임의로 계산하거나 누락값을 정상으로 간주하지 않고 안내 메시지를 표시한다.
- API 연결 실패 및 예측 요청 실패 시 사용자가 상황을 파악할 수 있도록 오류 메시지를 표시한다.
- 합성 데이터와 Mock 예측 결과가 실제 임상 판단에 사용될 수 없다는 안내를 추가했다.

### 2.2 API 클라이언트 (`api_client.py`)

- 대시보드에서 FastAPI의 상태 확인 및 예측 엔드포인트를 호출할 수 있도록 클라이언트 함수를 구성했다.
- 요청 타임아웃을 설정해 API 응답을 무한정 기다리지 않도록 했다.
- 일시적인 요청 실패에 대해 제한된 횟수로 재시도하도록 했다.
- 응답이 예상한 JSON 객체 형태인지 검증하도록 했다.
- 오류 발생 시 대시보드에서 적절한 안내를 표시할 수 있도록 예외를 처리하는 흐름을 구성했다.

### 2.3 코드 변경 범위

이번 D 담당 작업에서 수정한 파일은 다음과 같다.

- `src/icu_sews/dashboard/app.py`
- `src/icu_sews/dashboard/api_client.py`

`Dockerfile.dashboard`, 데이터베이스 스키마, 모델 학습 코드 및 API 서버의 실제 모델 구현은 이번 작업에서 수정하지 않았다.

## 3. 설계 변경 사항

이번 작업에서는 데이터베이스 스키마를 변경하지 않았다. 대시보드가 모델 산출물을 직접 불러오는 대신 FastAPI를 통해 상태와 예측 결과를 전달받는 구조를 유지하면서, UI와 API 클라이언트 계층을 연결했다.

화면 검증에는 실제 환자 데이터가 아닌 합성 데모 환자 3명을 사용했다. 24시간 차트는 슬라이더의 현재 값을 시간 지점별로 반복한 데모 데이터이므로, 실제 환자의 시간에 따른 변화나 임상적 추세를 나타내지 않는다.

또한 API 응답에 SOFA, qSOFA 및 Calibration 정보가 포함되지 않을 수 있다는 점을 고려해, 해당 값을 프론트엔드에서 임의로 생성하지 않고 실제 응답에 포함된 정보만 표시하도록 했다.

## 4. 주요 기능별 개발 진척도 및 데모

| 기능 | 현재 상태 | 확인 방법 및 결과 |
|---|---|---|
| 환자 선택 | 구현 | 데모 환자 선택 메뉴 확인 |
| 생체징후 입력 | 구현 | 5개 슬라이더 구성 |
| 시계열 차트 및 관찰값 표 | 구현 | 차트와 표 화면 확인 |
| API 상태 확인 | 구현 | `/health` 요청 흐름 구성 |
| 위험도 요청 및 결과 표시 | 로컬 데모 확인 | 버튼 클릭 후 위험 점수와 분류 표시 |
| 특징값 표시 | 조건부 구현 | API 응답에 관련 필드가 있을 때 표시 |
| SOFA/qSOFA/Calibration | API 응답 의존 | 데이터가 없을 때 안내 메시지 표시 |
| 실제 모델 기반 예측 | 미완료 또는 미검증 | 현재 화면에 Mock 예측 안내 표시 |

로컬 실행에서는 `DEMO-001`에 대한 위험도 요청 후 **15.0% 점수와 Normal 분류**가 표시되는 것을 확인했다. 모델 버전은 `mock-scaffold-v1`로 표시되었다. 이는 데모 요청 및 결과 표시 흐름이 동작했다는 의미이며, 실제 모델의 예측 정확도나 임상적 유효성이 검증되었다는 의미는 아니다.

## 5. 팀원들이 현재 결과물을 확인하는 방법

현재 결과물은 외부 배포 전 단계이므로, 팀원 각자의 컴퓨터에서 저장소를 내려받고 Docker로 실행해 확인할 수 있다.

### 실행 방법

1. [ICU-SEWS 저장소](https://github.com/sogang-icu-sews/ICU-SEWS)를 열고 코드를 내려받거나 Git으로 clone한다.
2. 컴퓨터에 Docker Desktop을 설치하고 실행한다.
3. 저장소 루트 폴더에서 터미널을 열고 다음 명령어를 실행한다.

   ```bash
   docker compose up --build
   ```

4. 브라우저에서 아래 주소를 연다.
   - 대시보드: http://localhost:8501
   - FastAPI 문서: http://localhost:8000/docs
5. 대시보드에서 DEMO 환자를 선택하고 입력값을 변경한 뒤 예측 요청을 실행해 결과가 표시되는지 확인한다.

종료할 때는 실행 중인 터미널에서 `Ctrl+C`를 누르고, 필요하면 `docker compose down`을 실행한다.

**참고:** `localhost` 주소는 각 팀원 본인의 컴퓨터에서만 열리는 주소이므로, 이 주소를 그대로 공유해도 다른 팀원이 접속할 수 있는 것은 아니다. 현재는 각자 로컬에서 실행하는 방법이며, 링크만으로 접속하도록 하려면 별도 외부 배포가 필요하다. 지금 표시되는 예측은 Mock 데모 결과이므로 실제 환자 데이터나 임상 판단에 사용하면 안 된다.

## 6. 향후 계획에 대한 팀원 의견 요청

다음 개발 단계의 우선순위를 정하기 위해 팀원들의 의견을 받고자 한다. 아래 질문에 대해 회의 또는 GitHub PR 댓글로 의견을 남겨 주면 좋겠다.

1. **다음 단계의 최우선 목표는 무엇인가?** 실제 모델 연동 및 검증, 외부에서 접속할 수 있는 데모 배포, 대시보드 UI 개선 중 어떤 것을 먼저 진행하는 것이 좋을까?
2. **대시보드에서 가장 먼저 보강해야 할 기능은 무엇인가?** 예를 들어 실제 시계열 데이터, 위험도 추이, 특징값 설명, 오류 상태 안내 중 우선순위가 높은 항목은 무엇인가?
3. **예측 API 응답에 어떤 항목이 꼭 필요할까?** 위험 점수와 분류 외에 모델 버전, SHAP 설명, SOFA/qSOFA, Calibration 정보 중 실제 백엔드에서 제공할 항목과 형식을 합의할 필요가 있다.
4. **외부 데모 배포 시 어떤 접근 범위가 적절할까?** 링크를 가진 팀원 누구나 접근하는 공개 데모로 충분할까, 아니면 인증이나 접근 제한이 필요할까?
5. **통합 테스트는 어떤 기준으로 완료라고 판단할까?** 정상 요청, API 장애, 잘못된 응답, 환자 변경, 실제 모델 연결 여부 등에 대해 팀 공통의 확인 기준을 정할 필요가 있다.

의견을 취합한 뒤 우선순위를 합의하고, 실제 모델 연결 및 검증 상태와 데모 배포 여부를 구분해 다음 작업 계획을 확정할 예정이다.

## 7. 남은 일정 및 최종 목표

향후에는 백엔드 담당과 협업하여 API 계약과 실제 모델 연동을 확인하고, 통합 테스트를 진행할 예정이다.

1. **API 스키마 확인:** 백엔드 담당과 요청·응답 필드명, 자료형 및 오류 응답 형식을 재확인한다.
2. **실제 모델 연동 검증:** 모델 로드 상태, Mock 여부 및 예측 결과가 화면에 올바르게 표시되는지 확인한다.
3. **임상 지표 연동 확인:** SHAP 설명, SOFA/qSOFA 및 Calibration 정보가 실제로 제공될 때 화면에 정확하게 표시되는지 확인한다.
4. **오류 상황 테스트:** API 서버 중지, 타임아웃, 잘못된 응답 등 다양한 실패 상황에서 적절한 오류 안내가 표시되는지 확인한다.
5. **환자 변경 테스트:** 환자 선택 및 입력값 변경 후 다시 요청했을 때 이전 환자의 결과가 잘못 표시되지 않는지 확인한다.
6. **최종 통합 테스트:** UI, API 및 실제 모델을 통합한 뒤 팀원들과 함께 기능 및 자동 품질 검사를 재확인한다.

최종 목표는 실제 모델과 API 응답 계약에 맞게 대시보드를 통합하고, 정상 요청뿐 아니라 오류 상황에서도 사용자가 결과와 시스템 상태를 명확하게 확인할 수 있도록 하는 것이다.
